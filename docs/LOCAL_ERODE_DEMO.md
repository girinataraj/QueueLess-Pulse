# Local Erode Eye Clinic demonstration

This local worktree starts from approved commit `f895908340c589d1730b061de964d1fe63323783`, on `feat/erode-local-demo`. It does not include Antigravity's pending changes. No hosted service, remote Git branch or existing PostgreSQL cluster is used or changed.

The clinic is fictional: **Erode Eye Clinic — DEMO**, Erode, **Main Reception**, **Eye Consultation**, prefix **E**. Use synthetic information only.

## Start and stop

Run in PowerShell:

```powershell
Set-Location 'C:\Users\girin\.codex\worktrees\erode-local-demo\DR'
& 'E:\Internship\New folder\DR\.venv\Scripts\python.exe' .\scripts\local_demo.py setup
& 'E:\Internship\New folder\DR\.venv\Scripts\python.exe' .\scripts\local_demo.py start
```

The existing Python environment is reused for packages only. The helper overrides inherited database settings before importing Flask. Setup and start verify the exact database/server identity before schema creation or seeding. Start also starts this local PostgreSQL instance if stopped. Keep the terminal open. If the demo is already running, open its URL instead of starting another copy on port 5000.

Alternatively, ` .\scripts\start-local-demo.ps1 -Action start` resolves that Python environment automatically. This wrapper changes no Windows service or firewall settings.

Stop Flask with Ctrl+C in its terminal. To stop only this new PostgreSQL cluster afterward:

```powershell
& 'E:\Internship\New folder\DR\.venv\Scripts\python.exe' .\scripts\local_demo.py stop-postgres
```

React assets are built and served by Flask, without a separate Vite server. To rebuild from the pinned lockfile:

```powershell
npx --yes pnpm@11.25.0 --dir frontend install --frozen-lockfile --strict-peer-dependencies
npx --yes pnpm@11.25.0 --dir frontend run build
```

## Private access and interfaces

Open `.tmp/PRIVATE_LOCAL_DEMO_ACCESS.md` privately for the generated browser-gateway, Owner, Doctor and Receptionist passwords, URLs and database password. `.tmp/PRIVATE_RECEPTION_ACCESS.md` contains only the gateway and read-only Reception instructions. Both files have Windows permissions restricted to the current user and are Git-ignored. Never paste their contents into chat or publish them.

Every interface requires the separate local HTTP Basic gateway. Enter those credentials in the browser prompt first. Then sign in to the application with the relevant account. Use separate browser profiles for Owner and Doctor, or log out before switching accounts.

| Interface | URL |
| --- | --- |
| Directory | http://127.0.0.1:5000/app/ |
| Reception: actual service QR and live queue counts | http://127.0.0.1:5000/static/local-demo/reception.html |
| Patient: Eye Consultation | http://127.0.0.1:5000/app/b/erode-eye-clinic-demo/service/1 |
| Doctor: assigned Staff console | http://127.0.0.1:5000/app/staff/login |
| Owner | http://127.0.0.1:5000/app/owner/login |
| Public Display, protected by demo gateway | http://127.0.0.1:5000/app/b/erode-eye-clinic-demo/display |
| Completed consultation history | http://127.0.0.1:5000/app/owner/business/1/history?status=COMPLETED |

Owner has the existing Owner authorization. Doctor has an ACTIVE Staff membership and the Eye Consultation assignment. Receptionist has an ACTIVE Staff membership with no clinical service assignment or Owner rights. The read-only Reception page requires only the gateway; application sign-in is optional there. A Receptionist opening the Staff console sees no assigned queues by design. The Doctor sees the assigned queue.

The QR is generated by the existing authenticated Owner QR endpoint and saved to ignored `static/local-demo/eye-consultation-qr.png`. It opens the real service URL. Reception polls the existing display API every three seconds; it never invents statistics or embeds an iframe that would bypass the application's frame protection. Owner can regenerate/download QR codes from the service card in the existing dashboard.

## Initial persisted records and demonstration order

The first successful setup creates these real queue records through the existing authenticated APIs, with their normal audit events and the clinic's current Asia/Kolkata business date:

| Status | Count | Tokens |
| --- | ---: | --- |
| Completed today | 7 | E001–E007 |
| Skipped today | 2 | E008–E009 |
| Called | 1 | E010 |
| Waiting | 5 | E011–E015 |

Repeated setup does not reset records, duplicate them or undo demonstration actions. The fixture is created once; it is not automatically replenished or changed to a new date on later days.

1. Open Reception. Confirm E010 serving and 5 waiting; show the actual QR.
2. Open its Patient link in a separate browser context. Join Queue. Initially this produces E016, with six people ahead and an approximate 30-minute wait. Later runs produce the actual next number.
3. Sign in as Doctor. Complete E010, which is already called; Call Next is intentionally disabled while a ticket is being served.
4. Call E011 and Skip it to demonstrate skipping. Call and Complete E012–E015 in FIFO order.
5. Call E016. Patient and Public Display update automatically. Complete E016 to mark the consultation reviewed.
6. Sign in as Owner and open Completed history. Verify E016, today's business date and its CREATED / CALLED / COMPLETED audit trail. Reception shows zero waiting and no current token after this sequence.

The browser acceptance tests exercise this sequence in disposable test schemas in the same isolated local database. The displayed `public` schema retains the original 15 records. Test schemas are kept separately for inspection; they do not add clinics to the displayed application.

The PostgreSQL 18.6 data directory is `.tmp/postgres18-data` inside this worktree. Persistent configuration listens only on 127.0.0.1. Host authentication and stored passwords use SCRAM-SHA-256. The application role owns its database but is not a superuser and cannot create databases, roles or replication connections. The separate bootstrap administrator password is in ignored `.tmp/local-demo-private.json`, not required for application access.

Connection, authentication and role evidence: `evidence/local-postgres-verification.json`. Both `psql` and SQLAlchemy verify the actual database, host, port and application role. These checks never use inherited Render credentials.

## Verification and limits

```powershell
$env:RUN_LOCAL_DEMO_ACCEPTANCE='1'
& 'E:\Internship\New folder\DR\.venv\Scripts\python.exe' -m pytest .\scripts\verify_local_demo_browser.py -q --junitxml=evidence/local-demo-browser.xml
```

The three acceptance tests cover desktop (1366×900), mobile viewport (390×844), and read-only validation of the running port-5000 demo. They include gateway rejection, active Doctor assignment, Receptionist authorization boundaries, QR decoding, idempotent seeding, issued-ticket reload, ETA, FIFO call/skip/complete, automatic Reception/Public Display updates, persisted Owner history and unchanged main demo counts. Frontend checks use the existing strict TypeScript build, ESLint and 14 Vitest tests.

This is a local synthetic-data demonstration. No deployment or real patient data is authorized. Owner overview metrics cover all recorded tickets; use the history business-date column and dated throughput chart to identify today's consultations. There is no dedicated Today's Reviews screen or date-filter control in this approved baseline.

The current QR points to 127.0.0.1 and works on this computer. On a physical phone, localhost refers to the phone. Physical phone scanning has not been verified. Before phone use, arrange a trusted private LAN and a browser-compatible secure origin, regenerate the QR for that address and retain the gateway. The approved React Join Queue uses `crypto.randomUUID`, which needs a secure browser context; plain LAN HTTP is not sufficient in ordinary phone browsers. Do not expose this development server to the public internet or forward its port. The wrapper's optional LAN address binds a specific trusted local interface but does not provide HTTPS or change firewall rules.
